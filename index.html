Sheet 02/07 REMS · Property and rental management Scale: NTS Rev C

Property and Rental Management System

Multi-role platform for letting agencies · Laravel + Angular · 2026

REMS covers the whole tenancy: an owner registers a property, units are listed and approved, an agent drafts a tenancy, a tenant moves in, rent is invoiced on a billing cycle, payments are matched to those invoices, and the deposit is refunded when the tenancy ends. Maintenance tickets, vacate notices and agent commissions run alongside. That is about twenty REST resources, all behind token login with role-based permissions.

The domain is unforgiving in two ways. A unit let to two tenants at once is a legal problem, not a bug report. And money that does not reconcile is worse than having no system at all.

A

Making double-letting impossible, not just unlikely

The obvious fix is to check for an active tenancy before activating a new one. That check passes for both requests when two agents click at the same moment.

Agent A · 10:02:14.031Activate tenancy 41 on unit 7
Agent B · 10:02:14.033Activate tenancy 42 on unit 7
PostgreSQL · tenancies Both checks said "unit 7 is free".
39 · unit 7ended
41 · unit 7active
uniq_active_tenancy_per_unit
WHERE status = 'active'
A · 200 OKTenancy 41 is active
B · 422Unit 7 already has an active tenancy
Rejected by index
Detail A · read top to bottom · not to scale

So the rule lives in the database instead:

CREATE UNIQUE INDEX uniq_active_tenancy_per_unit
  ON tenancies (unit_id) WHERE status = 'active';

A partial unique index lets a unit collect any number of draft and ended tenancies but allows exactly one active row. The second request now fails in the database however the two overlap, and the controller turns that into a clean 422. The rule holds even if someone later writes a script that skips my code.

Payments get the same care in code: an amount is refused unless it fits both the payment's unallocated balance and the invoice's outstanding balance. Invoice status is worked out from the allocations inside the same transaction, and when an allocation moves, both invoices are recalculated.

One deliberate choice: the backend uses Laravel's query builder rather than Eloquent, with only User and Role as models. I wanted explicit SQL and no surprise N+1 queries. The cost is real (no relationships, no casts, some repeated validation), and it is a trade I would revisit on a bigger team.

Sheet 03/07 EquiTask · Fair workload allocation Scale: NTS Rev C

EquiTask

Fair workload allocation · Django + React · Capstone, Riara University

Task managers let you assign work, but they do not tell you whether you were fair. EquiTask recommends who should take each task, then measures whether the result was actually even, scoring every candidate on skill match, current load, track record, fairness and urgency.

B

Not trusting a small sample, and saying so

Someone who finished two tasks on time does not have a 100% record. They have almost no record. Ranking them above a colleague with forty solid completions would be unfair, so scores are pulled toward a neutral starting value until there is enough history: 

score = (n × observed + K × prior) / (n + K)
# K = 5, prior = 0.6

A confidence value travels with each recommendation, and each one comes with a plain-language reason: which skills matched, which are missing, roughly how many hours that person already carries, and whether there is enough history to trust the number. A system that ranks people has to be able to justify itself.

The weights are not hardcoded either. A scheduled job joins past recommendations to how they turned out, fits a logistic regression, and saves a new versioned set of weights. It refuses to train on fewer than fifty samples or when nothing actually predicts success.

Fairness is measured, not eyeballed: a Gini coefficient and coefficient of variation over the team's workload, with each person banded by their ratio to the team average. Daily metrics are worked out ahead of time so the dashboard reads totals instead of recalculating history on every load.

Sheet 04/07 PR Concierge · GitHub App Scale: NTS Rev C

PR Concierge

GitHub App for reviewable pull requests · TypeScript + Octokit · 2026

Reviews stall for boring reasons: a pull request is too big to read in one sitting, does not say why it exists, or waits on a reviewer who has forgotten it. PR Concierge labels every pull request by size (ignoring lockfiles and generated files), keeps a short checklist of what is missing, and nudges reviewers when things go quiet. Each repository can tune or switch off any feature with a YAML file.

C

Useful on every push without becoming noise

<!-- pr-concierge:checklist -->
# found by its marker: edited only if the text changed
# not there yet and everything passes: stay quiet

Pull requests already in good shape never get a comment, and an unchanged checklist costs no write at all. Reminders use the same idea without a database: a pull request is stale when nobody has touched it for a few days, and posting the reminder counts as a touch, so each one is nudged at most once per stale period. Staying stateless is what lets it run as one serverless function on a free plan.

Setup is one click: a local page registers the app through GitHub's manifest flow and saves its credentials, so nobody copies keys between browser tabs.

Sheet 05/07 VHS Video Store · Movie discovery Scale: NTS Rev C

VHS Video Store

Movie discovery with an 80s look · Next.js + Firebase · 2026

A movie discovery app made to look like it came off a rental shelf in 1987: CRT scanlines, film grain and a slow flicker, all in CSS rather than image overlays. Underneath: TMDB search and trending, movie pages, real-time favourites, and several named watchlists with live counts.

D

Choosing a key so duplicates cannot exist

Favourites and watchlist items use each movie's TMDB id as the Firestore document id:

users/{uid}/favorites/{movieId}
users/{uid}/watchlists/{listId}/items/{movieId}

With a random id I would need a read-then-write to avoid adding the same film twice, and that can race. Keying on the movie id makes toggling safe to repeat and duplicates impossible: the same idea as the index in REMS, applied to a document store. List counts use atomic increments, so a watchlist costs one read however long it is, and ownership is enforced in Firestore security rules rather than assumed by the interface.
