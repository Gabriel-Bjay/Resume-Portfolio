Property & Rental Management System

Multi-role platform for letting agencies · Laravel + Angular · 2026

REMS covers the full tenancy lifecycle: an owner registers a property, units are listed and approved, an agent drafts a tenancy, a tenant moves in, rent is invoiced on a billing cycle, payments arrive and get reconciled against those invoices, and deposits are refunded when the tenancy ends. Maintenance tickets, vacate notices and agent commissions run alongside it — around twenty REST resources, all behind token auth with role-gated permissions.

The domain is unforgiving in two specific ways. A unit let to two tenants at once is a legal problem, not a bug report. And money that doesn't reconcile is worse than no system at all.

Making double-letting impossible rather than unlikely

The obvious approach is to check for an existing active tenancy before activating a new one. That check passes for both requests when two agents activate at the same moment. So I moved the rule into the database: 

CREATE UNIQUE INDEX uniq_active_tenancy_per_unit
  ON tenancies (unit_id) WHERE status = 'active';

A partial unique index lets a unit accumulate any number of draft and ended tenancies while permitting exactly one active row. The second request now fails at the storage layer no matter how the two interleave; the controller catches it and returns a clean 422. The invariant holds even if someone later writes a script that bypasses my code entirely.

Payment allocation got the same treatment in application logic: an amount is rejected unless it fits within both the payment's unallocated balance and the invoice's outstanding balance. Invoice status is then derived from the sum of allocations inside the same transaction — and when an allocation moves between invoices, both get recalculated.

One decision I'd flag as deliberate: this backend uses Laravel's query builder throughout rather than Eloquent, with only User and Role as models. I wanted explicit SQL and no accidental N+1s or lazy-loading surprises. The cost is real — no relationships, no casts, and validation rules repeated between create and update — and it's a trade I'd revisit on a larger team.

EquiTask

Fair workload allocation · Django + React · Capstone, Riara University

Task managers let you assign work, but they don't tell you whether you've been fair about it. EquiTask recommends who should take each task, then measures whether the resulting distribution was actually equitable — scoring every candidate across skill match, current load, track record, fairness and urgency.

Building a system that ranks people meant the hard problems were statistical and social rather than architectural. Two stand out.

Not trusting a small sample, and saying so

Someone who has completed two tasks on time doesn't have a 100% reliability record — they have almost no record at all. Scoring them above a colleague with forty solid completions would be indefensible. So performance scores are shrunk toward a neutral prior in proportion to how much history exists: 

score = (n × observed + K × prior) / (n + K)
# K = 5, prior = 0.6 — with n=2 the score
# sits near the prior; by n=40 it barely moves it

A separate confidence value, saturating at five recorded outcomes, travels with each recommendation. And every recommendation carries a plain-language rationale — which required skills matched, which are missing, roughly how many hours that person is already carrying, and whether there's enough history to trust the number. An allocation system nobody trusts is one nobody uses, so it had to be able to justify itself.

The weights aren't hardcoded either. A scheduled job joins past recommendations to their recorded outcomes, fits a logistic regression to find which components genuinely predicted success, and saves a new versioned weight set — refusing to train on fewer than fifty samples, on single-class outcomes, or when nothing positively predicts success. It learns, and it knows when not to.

Fairness itself is measured properly rather than eyeballed: a Gini coefficient and coefficient of variation over the team's workload vector, with members banded by their ratio to the team mean. Daily per-user metrics are precomputed by a Celery job so the dashboard reads aggregates instead of recomputing history on every load.

VHS Video Store

Movie discovery with an 80s aesthetic · Next.js + Firebase · 2026

A movie discovery app built to look like it came off a rental shelf in 1987 — CRT scanlines, film grain and a slow flicker, all in CSS rather than image overlays. Underneath it: TMDB search and trending, movie detail pages, real-time favourites, and multiple named watchlists with live counts.

Choosing a document key so duplicates can't exist

Favourites and watchlist items are stored under per-user subtrees, using each movie's TMDB id as the Firestore document id: 

users/{uid}/favorites/{movieId}
users/{uid}/watchlists/{listId}/items/{movieId}

With an auto-generated id I'd have needed a query-then-write to avoid adding the same film twice, which races. Keying on the movie id instead makes toggling naturally idempotent and duplicates structurally unrepresentable — the same instinct as the database index in REMS, applied to a document store.

List counts are maintained with atomic increments rather than counting documents on read, so a watchlist costs one read regardless of size. Updates arrive through snapshot listeners rather than polling, each cleaned up on unmount. Ownership is enforced in Firestore security rules, so it's a real boundary rather than a UI assumption.

The app also documents itself: an in-app page renders the system architecture as a diagram, which turned out to be the fastest way to explain the project to anyone new.

PR Concierge

GitHub App for reviewable pull requests · TypeScript + Octokit · 2026

Reviews stall for boring reasons: a pull request is too big to read in one sitting, doesn't say why it exists, or waits on a reviewer who has forgotten it. PR Concierge labels every pull request by size, ignoring lockfiles and generated files, keeps a short checklist of what's missing, and nudges reviewers when a review has gone quiet. Each repository can tune or switch off any feature with a YAML file.

Useful on every push without becoming noise

The app re-runs whenever a pull request changes. Posting a fresh comment each time would bury the conversation, so the checklist is a single comment that the app finds again by a hidden marker and edits in place: 

<!-- pr-concierge:checklist -->
# found by its marker: edited only if the text changed
# not there yet and everything passes: stay quiet

Pull requests that are already in good shape never get a comment, and an unchanged checklist costs no write at all. Reminders use the same idea without a database: a pull request is stale when it hasn't been touched for a few days, and posting the reminder counts as a touch, so each one is nudged at most once per stale period. Keeping the app stateless is what lets it run as a single serverless function on Vercel's free plan.

Setup takes one click: a local page registers the app through GitHub's manifest flow and saves its credentials, so nobody copies keys between browser tabs.
